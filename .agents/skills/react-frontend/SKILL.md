# React Frontend Engineering

Build production-quality React Web user interfaces that are accessible, performant, maintainable, and visually polished. The goal is UI that looks like it was built by a design-aware frontend engineer at a top company — not like it was generated by an AI. This means adhering to the project's design system, implementing proper accessibility, using thoughtful interaction patterns, and maintaining clean component architecture.

---

## When to Use

- Building new React components, pages, or user-facing layouts for web applications.
- Modifying or refactoring existing user interfaces.
- Implementing responsive layouts and mobile-first design.
- Adding client/UI interactivity, state management, or custom hooks.
- Auditing or fixing visual quality, contrast, accessibility, or UX issues.
- Initializing or updating a project-specific design system (`MASTER.md`) when explicitly requested by the user.

**Skip this skill** for pure backend services, database schemas, API controllers, or non-visual build scripts unless the task directly impacts user-facing UI/UX.

---

## Technology & Project Compatibility

- Follow the project's existing React version, framework, styling approach, and component library.
- Do not introduce or migrate technologies unless explicitly requested or technically necessary.
- Treat framework-specific guidance (Next.js, React 19, Tailwind, shadcn/ui) in `data/stacks/` as conditional, not universal requirements. Only apply them when the project actually uses that specific technology and version.

## Workflow

Follow this execution workflow for every frontend task:

### 1. Identify Task Scope
Classify the task before inspecting files:
- **Logic-only / Non-visual Tasks:** Pure state refactoring, custom hook logic, API integrations, utility functions, bugfixes in event handlers, or unit tests.
  - *Action:* Execute directly using minimal-scope inspection on the relevant files. **Do not check or read `MASTER.md`**.
- **UI / Visual Tasks:** Creating new pages/components, modifying layouts, styling, adjusting tokens, or redesigning interfaces.
  - *Action:* Proceed to Step 2 to align with the visual design system and component reuse standards.

### 2. Check Design System Context *(UI/Visual Tasks Only)*
- Check if `docs/design-system/MASTER.md` (or `design-system/MASTER.md`) exists.
- **If `MASTER.md` exists:** Treat it as the primary source of truth for the project's visual identity and design conventions. Consult external reference datasets only when additional guidance is needed (e.g. specialized UX guidelines), without overriding established project decisions.
- **If `MASTER.md` is missing:** Follow the project's existing design conventions (CSS custom properties, Tailwind theme, and existing UI components). Consult [`references/design-system-guide.md`](references/design-system-guide.md) for curated styles, colors, typography, and UX guidelines when design guidance is needed. **Do not create `MASTER.md` automatically.**
- **Creating or updating `MASTER.md`:** Only create or update `MASTER.md` when the user **explicitly requests** establishing, harmonizing, or updating the project design system. See the step-by-step workflow in [`references/design-system-guide.md`](references/design-system-guide.md).

### 3. Inspect Before Implementing (Component Discovery)
Before writing code or creating components, search for relevant existing building blocks across the project:
1. **UI Components:** Check shared primitives and reusable components (e.g. `Button`, `Avatar`, `Dialog`, `Input`, `Card`, `Dropdown`, `DataTable`).
2. **Domain Components:** Check feature-specific components (e.g. `UserAvatar`, `UserCard`, `ConversationItem`, `MessageItem`, `ProductCard`).
3. **Existing Compositions:** Inspect how components are combined in similar existing features (e.g. `MessageList`, `ChatHeader`, `FilterToolbar`).
4. **Installed UI Libraries:** Check if the project already provides suitable components (e.g. shadcn/ui, Radix primitives, Headless UI) before implementing custom alternatives.

> [!TIP]
> **Search by Function, Not Just Exact Name:** Project naming varies. If looking for an avatar, check for `ProfileImage`, `UserIcon`, or `AvatarImage`. If looking for a modal, check for `Dialog`, `Popup`, or `Sheet`.

### 4. Implementation (Reuse & Composition Priority)
Apply the **Component Reuse & Composition Priority**:
1. **Reuse:** Use existing components when they satisfy the requirements.
2. **Compose:** Combine existing smaller components to build more complex interfaces.
3. **Extend:** Add variants, props, or composition capabilities to existing components when appropriate.
4. **Create:** Introduce new components only when existing solutions cannot reasonably satisfy the requirements.

Keep components focused (< ~200 lines as heuristic), separate data fetching from presentation, and cross-reference interaction specs in [`references/component-specs.md`](references/component-specs.md) when building complex controls (modals, menus, tables).

### 5. Sync & Task-Relevant Verification
- If `MASTER.md` exists and the user explicitly requested global style changes affecting the design system, update `MASTER.md` to keep it synchronized.
- Verify only the behaviors and states relevant to the current task:
  - Component renders cleanly without console errors or introduced warnings.
  - Interactive controls are keyboard accessible and have visible focus.
  - Responsive layout behaves correctly across relevant viewports.
  - Dynamic data states (loading skeleton, empty, error) handled where applicable to the feature.

## Component Reuse & Composition

Prioritize reuse over recreation. Before creating a new component, inspect the relevant existing components and project conventions.

### Reuse Priority
1. **Reuse:** Use existing components when they satisfy the requirements.
2. **Compose:** Combine existing components to build more complex interfaces.
3. **Extend:** Add variants, props, or composition capabilities to existing components when appropriate without breaking existing usage.
4. **Create:** Introduce new components only when existing solutions cannot reasonably satisfy the requirements.

### Guidelines
- Do not recreate components that already exist in the project or its installed UI library.
- Prefer composition (children/slots) and established component APIs over duplicating markup, styling, or interaction logic.
- Preserve existing component contracts and avoid unnecessary breaking changes.
- Keep abstractions reusable, but do not force unrelated UI into an overly complex shared component.
- Avoid creating one-off wrappers or excessive micro-components without a clear benefit.
- Before introducing a dependency or UI library, check whether the project already provides an equivalent solution.

**Decision Rule:** A new component must have a clear responsibility and a justified reason for existing independently. Reuse and composition are preferred, but should not compromise readability, maintainability, or feature-specific requirements.

## Component Architecture & Patterns

### 1. Composition Over Mega-Prop Configuration
Prefer composable sub-components and slots (`children`) over brittle mega-prop configurations:

```tsx
// Good: Composable via sub-components / slots
<Card>
  <CardHeader><CardTitle>Active Tasks</CardTitle></CardHeader>
  <CardContent><TaskList items={tasks} /></CardContent>
</Card>

// Avoid: Brittle mega-prop configuration
<Card title="Active Tasks" showHeader items={tasks} contentPadding="md" />
```

### 2. Separation of Concerns & State Coverage
Separate data fetching, mutation hooks, and async state lifecycle from pure presentational rendering:

```tsx
// Container: Manages data fetching, lifecycle states, and mutations
export function TaskListContainer() {
  const { data, isLoading, error, refetch } = useTasks();

  if (isLoading) return <TaskListSkeleton />;
  if (error) return <ErrorState message="Failed to load tasks" onRetry={refetch} />;
  if (!data?.length) return <EmptyState message="No tasks yet" />;

  return <TaskList items={data} />;
}
```

### 3. Component Organization Guidelines
- **Follow project conventions:** Colocate related files (component, styles, tests, hooks) following the project's existing directory structure.
- **Heuristic limit (`~200 lines`):** Treat components exceeding ~200 lines as a practical guideline to consider extracting sub-components or custom hooks for maintainability.
- **Interactive Component Contracts:** For standard interaction specs, keyboard shortcuts, and accessibility contracts (modals, forms, menus, tables), refer to [`references/component-specs.md`](references/component-specs.md).

## State Management

Choose the simplest state approach based on actual requirements:

```text
Local UI state (useState)        → Component-specific interactive state
Lifted state                     → Shared between 2-3 sibling components
Context                          → Theme, auth, locale (read-heavy, write-rare)
URL state (searchParams)         → Filters, pagination, tabs, shareable UI state
Server state (TanStack Query)    → Remote data with caching, re-fetching, synchronization
Global store (Zustand, Redux)    → Complex client state shared app-wide (only when justified)
```

**Guidelines:**
- **Prop drilling heuristic:** When passing props through multiple levels becomes cumbersome, evaluate introducing context or restructuring component composition.
- **Compute derived state during render** instead of syncing with `useEffect` and redundant state variables.
- **Do not duplicate server data in client-side global stores.** Let your data-fetching layer manage server caching.
- **Optimistic Updates:** Use for lightweight, reversible UI actions (e.g. toggles, bookmarks); ensure query cache rollback on error. For critical mutations (payments, destructive actions), use explicit loading feedback.

## Accessibility (WCAG AA Target)

Ensure components meet contextual accessibility requirements:
- **Semantic HTML & Keyboard Navigation:** Use native `<button>` for actions and `<a href>` for navigation. Preserve their native keyboard behavior instead of recreating interactions with generic elements.
- **Visible Focus:** Ensure every operable control has a visible focus indicator (`focus-visible:ring-2`).
- **ARIA & Labels:** Add explicit `<label htmlFor="...">` for inputs, and `aria-label` for icon-only buttons (`<button aria-label="Close dialog"><XIcon /></button>`).
- **Focus Management:** For modals and dialogs, move focus into the dialog upon opening, trap focus within while active, and restore focus to trigger upon close.
- **Reference:** For comprehensive usability and accessibility rules, see [`data/ux-guidelines.csv`](data/ux-guidelines.csv) (or via [`references/design-system-guide.md`](references/design-system-guide.md)).

## UI State Coverage (Contextual)

Implement data states as appropriate for the feature being built:

### Skeleton Loading (Prevent Layout Shift)
For async data fetching views, use structured skeleton placeholders matching the layout geometry rather than generic spinners:

```tsx
function TaskListSkeleton() {
  return (
    <div className="space-y-3" role="status" aria-busy="true">
      <div className="h-10 bg-muted animate-pulse rounded-md" />
      <div className="h-10 bg-muted animate-pulse rounded-md" />
    </div>
  );
}
```

### Empty & Error States
When rendering dynamic collections, provide actionable empty states with next-step CTA buttons and clear error recovery (`onRetry`) where needed.

## Responsive Design

- Design mobile-first, layering breakpoint utilities for larger screens (`grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 gap-4`).
- Respect the project's existing responsive breakpoints (e.g. standard Tailwind `sm`, `md`, `lg`, `xl`).
- Test responsiveness across viewports relevant to the layout being built.

---

## Red Flags

- Scanning the entire codebase or reading `MASTER.md` for non-visual / logic-only tasks.
- Recreating components that already exist in the project or installed UI library.
- Creating one-off duplicates without checking for functionally equivalent components (e.g. creating `Avatar` when `ProfileImage` exists).
- Automatically creating `MASTER.md` when the user did not explicitly request establishing a design system.
- Extracting components into overly fine-grained fragments prematurely.
- Inline styles or arbitrary pixel values when design system tokens exist.
- Missing error, loading, or empty states when rendering dynamic collections.
- Interactive elements without visible focus indicators (`focus-visible`).
- Color as the sole indicator of state (red/green without accompanying text or icon).
- Introducing heavy external UI/state libraries without clear justification.

---

## Verification & Handoff

After completing the task, verify only what is directly applicable:
- **Component Reuse:** Leveraged existing project primitives and domain components where available.
- **Clean execution:** Component renders cleanly without console errors or introduced warnings.
- **Accessibility:** Interactive controls are operable via keyboard; focus indicators are visible.
- **Consistency:** Follows the project's established design conventions (and `MASTER.md` if established).
- **Concise handoff:** Provide a direct, focused confirmation of the changes made. Do not generate verbose commentary.
